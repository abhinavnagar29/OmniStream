# OmniStream

Cross-domain personalized recommendation platform (movies, video, music, podcasts, news) — a two-stage recommender (semantic ANN + collaborative filtering retrieval, learned ranking + MMR diversity) with a real offline evaluation harness, a real JWT-authenticated multi-user backend, and a designed (not templated) React frontend.

**Docs:** [`docs/architecture.md`](docs/architecture.md) (design rationale & tradeoffs) · [`docs/design.md`](docs/design.md) (frontend design system) · [`docs/deployment.md`](docs/deployment.md) (how to actually deploy this)

---

## What's real vs. simulated (read this first)

- **Movie catalog (1,500 items): real.** Sourced from a public TMDB snapshot committed in the repo (`backend/data/seed/tmdb_5000_movies.csv`), normalized, embedded, and ingested (`scripts/ingest/movies.js`).
- **Other domains (video/music/podcast/news, ~96 items): synthetic**, generated by a procedural content generator, tagged `source: 'synthetic-generator'` in the database so it's never ambiguous which is which.
- **Interaction data (23K+ rows, 300 users): simulated.** This project has no real user base yet, so `scripts/simulate/generateInteractions.js` generates genre-affinity-driven synthetic users and interactions to have something to train collaborative filtering on and evaluate against. Every downstream number (CF factors, evaluation metrics, ranker weights) is computed for real from this data — the *computation* is real, the underlying *behavior* is not.
- **Movie thumbnails** point at `picsum.photos` placeholders, not real posters — TMDB's image CDN wasn't reachable from the sandbox this was built in (see `docs/deployment.md` for the one-line swap to real posters).
- **Everything else** — schema, ingestion, retrieval, ranking, evaluation, auth, caching, the async pipeline, rate limiting, the frontend — is real, running, tested code, not a mockup.

## Features

**Recommender**
- Two-stage architecture: candidate generation (semantic ANN via pgvector HNSW + collaborative filtering + trending + cold-start) → ranking (heuristic score blended with a learned model) → MMR diversity re-rank.
- Offline collaborative filtering (implicit ALS matrix factorization) and Learning-to-Rank (LightGBM LambdaMART), both trained and genuinely evaluated — see results below.
- Per-item explainability ("why was this recommended") grounded in the actual ranking features, not decorative text.
- Deterministic A/B experiment assignment + an impressions/clicks join for offline analysis.

**Backend**
- Real persistence: PostgreSQL 16 + pgvector, replacing an original in-memory prototype entirely.
- JWT auth (bcrypt + signed tokens), multi-tenant, every route scoped to the authenticated user.
- Redis-backed recommendation caching (invalidated on like/unlike/open/skip) and **distributed rate limiting** (shared across instances, not process-local).
- Async event pipeline (Redis Streams + a consumer-group worker with retry + dead-letter handling) for analytics events.
- Structured logging, OpenAPI docs (`/api/docs`), graceful shutdown, process-level crash handling.
- 62 automated tests (auth, recommendations, feedback, the async pipeline, rate limiting, and a dedicated error-handling/edge-case suite) against an isolated test database.

**Frontend**
- Real authentication flow: signup/login/logout, protected routing, session persistence, global 401 → logout and 429 → friendly-toast handling.
- A designed system, not defaults — see [`docs/design.md`](docs/design.md): a graphite-ink palette, one signal accent color, five distinct domain hues used consistently, Fraunces/Inter/IBM Plex Mono typography, and a recurring "spectrum bar" motif.
- Content detail modal merging full info + "why recommended" (fixes a real gap: most real movies have no external link to open).
- Mobile bottom navigation (the sidebar-only nav had zero mobile alternative before this).
- Toast notifications, skeleton loading states, domain quick-filters, password visibility toggles, a proper 404 page.
- Library, Journeys, and Search pages all share one interaction model (`useContentInteractions`) instead of three drifting implementations.

## Architecture

```
React Frontend (JWT auth, protected routes)
     │ REST + Bearer token
Express API (auth, Redis-backed rate limiting, structured logging, OpenAPI docs)
     │
     ├── Stage 1: Candidate Generation (candidateGeneration.js)
     │     ├── Semantic ANN retrieval (pgvector HNSW)
     │     ├── Collaborative filtering (offline-trained ALS factors)
     │     ├── Trending (popularity)
     │     └── Cold-start (onboarding-preference-based)
     │
     ├── Stage 2: Ranking (ranking.js)
     │     └── Heuristic score, optionally blended with a distilled
     │         learned-ranker model (see ml/train_ranker.py)
     │
     └── Diversity re-rank (diversityService.js — MMR)
     │
PostgreSQL 16 + pgvector (users, content, interactions, preferences,
recommendation_events, experiment_assignments, analytics_events)
     │
Redis (recommendation cache, rate-limit counters, async event stream)
     │
Async worker (scripts/worker/analyticsWorker.js) — Redis Streams consumer
group, retry + dead-letter queue, decoupled from the request path
```

## Local setup

Requires Node 20+, PostgreSQL 16+ with the `vector` extension available, and Redis.

```bash
npm install
cp .env.example .env   # fill in DATABASE_URL / REDIS_URL / JWT_SECRET

npm run db:migrate      # applies backend/db/schema.sql
npm run ingest           # real TMDB movies + synthetic other domains -> Postgres, with embeddings

npm run dev:backend     # http://localhost:5050
npm run dev:frontend    # http://localhost:3002 (proxies /api to the backend)
# or run both together:
npm run dev
```

Or with Docker (Postgres + pgvector, Redis, and the backend, one command):

```bash
docker compose up --build
docker compose exec backend npm run db:migrate
docker compose exec backend npm run ingest
```

API docs: `GET /api/docs` (Swagger UI) once the backend is running. Health check: `GET /api/health`.

**Optional — rebuild the ML artifacts** (pretrained versions are already committed under `ml/models/`, so this is only needed if you regenerate the simulated interaction data or want to retrain):

```bash
node scripts/simulate/generateInteractions.js   # simulated training/eval data -- see caveat above
pip install -r ml/requirements.txt
python3 ml/train_cf.py
python3 ml/train_ranker.py
python3 ml/evaluate.py                            # writes ml/evaluation_results.json
```

## Offline evaluation results

Real numbers from `ml/evaluate.py`, run on a per-user temporal leave-last-positive-out split (297 eval users, 101 candidates per user — see `docs/architecture.md` for the full protocol). Reproduce with `python3 ml/evaluate.py`; the script writes `ml/evaluation_results.json` fresh every run — these numbers are not hardcoded anywhere else.

| Model | Precision@10 | Recall@10 | nDCG@10 | MAP@10 | Topic entropy | Coverage@10 |
|---|---|---|---|---|---|---|
| Popularity baseline | 0.010 | 0.098 | 0.037 | 0.019 | 2.314 | 0.120 |
| Content-based only | 0.056 | 0.562 | 0.534 | 0.526 | 2.209 | 0.313 |
| Collaborative filtering only | 0.070 | 0.697 | 0.548 | 0.501 | 2.086 | 0.298 |
| Hybrid (content+CF+popularity, hand-weighted) | 0.056 | 0.556 | 0.441 | 0.405 | 2.186 | 0.279 |
| Hybrid + LightGBM LambdaMART ranker | 0.069 | 0.687 | 0.544 | 0.498 | 2.080 | 0.297 |
| Hybrid + ranker + MMR diversity | 0.069 | 0.687 | 0.543 | 0.497 | 2.105 | 0.296 |

**Honest reading**: all strategies clear the popularity baseline by a wide margin. The hand-weighted hybrid actually *underperforms* CF-alone and content-alone here — a real, slightly counterintuitive finding, not a typo — because fixed weights dilute a strong CF signal with less-informative recency/rating features. The learned ranker recovers most of that gap by *learning* the right feature weights instead of guessing them. MMR trades a small amount of nDCG for a real diversity gain. None of this is a "line goes up" story manufactured for a resume — it's what the run actually produced.

## Benchmarks (real, reproducible — not hardcoded)

**Brute-force vs. HNSW vector search** (`node scripts/benchmark/annBenchmark.js`, results in `ml/ann_benchmark_results.json`):

| Catalog size | Brute-force p50 | HNSW p50 | Speedup |
|---|---|---|---|
| 10,000 | 7.46ms | 1.53ms | 4.9x |
| 50,000 | 36.7ms | 2.13ms | 17.2x |
| 100,000 | 69.37ms | 4.08ms | 17.0x |

(Run on a 1-vCPU sandbox VM. At 100K, the default parallel HNSW index build didn't complete in a reasonable time on a single core — parallel maintenance workers were contending, not helping; a single-threaded rebuild succeeded. Full note in the results file.)

**Redis cache ON vs. OFF** (`GET /api/recommendations`, 15 concurrent connections, 12s, results in `load-tests/redis_on_vs_off_results.json`):

| | Requests/sec | p50 | p95 | p99 | CPU (~% of 1 core) |
|---|---|---|---|---|---|
| Redis ON | 988 | 12ms | 40ms | 55ms | 86.5% |
| Redis OFF | 88.25 | 165ms | 236ms | 242ms | 57.1% |

**11.2x throughput, 13.75x better p50 latency** with caching on. (CPU is *higher* with Redis on, in absolute terms — because ~11x more requests are served per second in the same window, so even cheap cache-hit handling adds up. A real, explainable nuance, not a contradiction.)

## Honest limitations

- Interaction data is simulated (see above) — every CF/ranker/eval number is real computation on synthetic behavior.
- 4 of 5 content domains are synthetic, not real data.
- The learned ranker served in Node is a distilled linear approximation of the LightGBM model that was actually evaluated (`ml/models/ranker_lgbm.txt` is the real one; `ranker_weights.json` is what's served, for latency reasons — see `docs/architecture.md`).
- Not deployed live yet (see "Deploying it" above).
- Frontend changes were verified via a real production build (`vite build`) and the full backend test suite, but not visually verified in an actual browser — this sandbox has none. If something looks wrong once you run it, that's the most likely source.
- No E2E (Playwright) tests, no fairness/bias analysis, no two-tower neural retrieval model.
